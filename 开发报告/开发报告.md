## 二、云端 agent：做了，然后整段删掉

### 起因
用户想让编程助手也能用云端 API（DeepSeek / 通义等）。截图上模型吐出了
`<|DSML| ...>` 这种东西，我们没有解析，任务当场结束。

### 撞到的三件事

1. **工具调用的形状，三家三套。**
   - OpenAI：发 `tools:[{type,function}]`，回 `delta.tool_calls` **碎片**
   - Anthropic：发 `tools:[{name,description,input_schema}]`，回
     `content_block_start` + `input_json_delta` **碎片**
   - Gemini：发 `functionDeclarations`，回 `functionCall`（一次给全）

   三套收发要**成对**维护。任何一处对不上，症状都是"模型收到了工具却永远调不回来"，
   而且界面上看不出来。

2. **"格式"是模型的训练习惯，不是接口的约定。**
   我们下发 `tools=`，渲染成什么形状是**模型聊天模板**说了算。它教 JSON 就吐 JSON，
   教 XML 就吐 XML，教 DSML 就吐 DSML —— 而 DSML 那种**连文档都没有**。
   实测还发现：连"我们自己在提示词里教它写 `<tool_call>`"这条退路也不可靠，
   模型会听自己训练里那套，不听我们的。

3. **连"它到底吐了什么"都拿不到一份干净的。**
   探针把 DSML 原文打出来，终端的转义/全角字符让 token 边界都无法确定。
   拿一个自己都没把握的格式写正则 = 埋一个坏解析器。

### 结论
不是"我们不行"，是**成本结构不对**：云端 agent 的力气大部分花在**适配和猜测**上，
不在功能上。而编程助手真正要的（稳定读文件 / 改文件 / 跑命令）本地模型完全够干。

### 删了什么 / 留了什么

| 删掉（`酒馆大脑.py` 1410 → 932 行） | 留着（**聊天链路一个字没动**） |
|---|---|
| `发工具` / `_函体`（逐协议换壳） | `流式`、`_备openai/_备anthropic/_备gemini` |
| `收碎片` + 三个收集器 | `_取*`、`_读客`、`_切SSE` |
| `拼工具碎片`、`_停因`、`_思维长` | `拼提示`、`窗口内`、`列模型` |
| `原生工具协议`、`_要原生` | 「接口配置」整张表和管理页 |
| `跑一轮` 的整个云端分支 | 云端聊天、云端模型清单 —— 照旧能用 |

`跑一轮` 现在只做一件事：不是 `local` 就明确报错，**不静默降级**。

## 三、本地 agent 的六个故障

全部是**跑真模型 / 真 tokenizer 复现出来的**，不是推演。

| # | 症状 | 真因 | 修法 | 验证 |
|---|---|---|---|---|
| 1 | 工具调用全废，报"解析失败" | **只认 JSON，Qwen3 系吐的是 XML**：`<function=write_file><parameter=path>…` | 新增 `_取XML调用` / `_取XML参数`，两种形状都认 | 同一个模型同一条任务复跑：抠出 `['write_file']`，内容 5684 字完整 |
| 2 | 提示词越过 `n_ctx`，llama.cpp 报错 | **预算估算低估 1.54 倍**（两个 bug 叠加，见下） | `抄本._尺寸` 按真正发出去的内容算；`估token` 重新标定 | 估/真 最小 1.05、平均 1.21，**永不低估** |
| 3 | "没写，还说完成了" | 模型某一轮**一个字都没输出**（思维链吃光输出预算），而"产出空"和"干完了"在数据上一样 | `_像在打算盘` 把空回复也算"没干完"；推两把还空就明确报错 | 假模型驱动：报 `空回复`，不再报"干完了" |
| 4 | 结构总是"上下文满了" | 装不下就**停任务**，而 `保留步数=6` 在步数少时**一步都不许折** | 撞上上限时先"拼命折"（保留压到 0），只剩存根还装不下才报错 | 3 步大文件：老的 10795 → 停；新的 576 → 继续 |
| 5 | 名字对不上就报"格式不合法" | `认得` 那道门槛**管错了地方** —— 它是防围栏 JSON 误判的，却把 `<tool_call>` 也管住了 | 门槛只管"猜"的两条路，`<tool_call>` 放行 | 原生模式下 `save_file` 现在会被喂回"没有这个工具，能用的只有…" |
| 6 | 格式崩了当场中止整个任务 | 不重试 | `_解析催话`：把上一轮原文 + 三条具体改法喂回去，最多 2 次 | 假模型：格式一直崩 → 3 次调用后停；崩两次后写对 → 正常继续 |
| 7 | **写出来的代码文件是坏的，而没人发现** | 模型在段落交界处**偶发漏换行**，把 `import time` 和 `def f():` 粘成一行 → `.py` 根本跑不起来 | `酒馆工具.语法提示`：写完/改完 `.py` **顺手 `compile()`**，语法错直接塞进工具结果 | 好文件空串、坏文件给出"第几行 + 那一行 + 怎么改"；落盘内容**不改一个字符** |

### 故障 7 是怎么定位的（值得记一下）

一开始怀疑是**流式读取丢了换行**，做了一次对照：

```
同一条提示，temperature=0
  非流式：967 字 / 53 换行   content 742 字   compile() 通过 ✓
  流式  ：967 字 / 53 换行   content 742 字   compile() 通过 ✓
两者逐字相等？是
```

**解析链路一个换行都没丢** —— 所以粘连是**模型自己吐的**（同一条提示跑两次，一次好
一次粘）。

于是**没有**在解析器里"把换行补回来"：那只能是**猜**，猜错就是静默写一个坏文件
（`改文件` 那段注释把这件事定过性 —— 比"读不到"糟糕一个数量级）。
改成**只报告、不改内容**，让模型自己重写。零额外模型调用、确定性、不用改提示词。

### 故障 2 的两个 bug（值得单独记）

**① `抄本._尺寸` 算的和 `抄本.消息` 发的不是同一份。**
前者算 `步['助手']`（正文），后者发 `步['原始'] or 步['助手']`（**原始输出优先**）。
模型把工具调用当文本吐时，`<tool_call>` 那段被从正文里挖掉了 —— **正文是空的**，
原始输出却有整整一个网页那么长。预算按"空"算，实际多出几千 token。

**② `估token` 的系数是错的。** 旧公式假设 ASCII **3.5 字一个 token** —— 那是
"自然英语散文"的数。用真 tokenizer 量了本项目 **25.7 万字**：

```
合计 257450 字 / 112217 token = 2.29 字/token
最密的文件               2.08 字/token
```

代码 / HTML 实测只有 **2.1~2.9**。新系数 **1.4 / 2.2**，实测估/真 1.05~1.34。

两个叠起来，正好是那次 `Requested tokens (4359) exceed context window of 4096`。

### 顺带实测出的一个 llama.cpp 事实

**它的上下文闸门只看提示词，不算 `max_tokens`：**

```
提示 1848 + 出 512 = 2360 / 2048 → 放行
提示 4400 + 出   8 = 4408 / 2048 → 报错
```

所以 `跑()` 里 `小号 + 单步出 > 上限` 比要求**更严**，多出来的那一份是白送的缓冲。

## 四、聊天链路：按窗口收口

### 病根
聊天只按**字符数**裁，`默认字数上限 = 24000`。按实测 2.2 字/token，
**24000 字 ≈ 10900 token** —— 对本地 4096 的窗口**必然超**。而且报错就是那句
天书，完全看不出是自己把上限设大了。

### 做法
新增 `酒馆大脑.窗口内(角色, 会话, 候选, 设定, 套)` —— **"发哪几条"的唯一判据**，
`酒馆对话页._拼` 和 `酒馆上下文页` 都换成它。它同时管：
- 会话设定的「条数 / 字数上限」
- **这套接口的 `n_ctx`**（只有本地才管；云端 `本机窗口()` 回 0，一个字不动）

做法是"**丢了重拼**"而不是估算该丢几条 —— 因为 `拼提示` 会把 `说话人='系统'`
的消息和"角色先开口"那句折进系统块，系统的实际大小**依赖消息集合**。

### 实测对比

20 条消息 × 1500 字，本地 `n_ctx=4096`：

```
老规矩（只按字数裁）  留 16/20 条   估 18254 token   → 必然超 ✗
新规矩（本地）        留  1/20 条   估  2174 token   → 装得下 ✓
云端走同一个函数      留 16/20 条   → 与改动前逐条一致 ✓
```

### 界面不再骗人
「上下文」页顶部会写明：这套是本地模型、窗口多少、**实际发几条由窗口决定**
（灰掉的就是没发的）。

老数据没有这一列 → 归一成「自动」→ 与改动前完全一致。

## 六、配置调优（实测，不是拍脑袋）

原配置：`n_ctx: 4096 / 8192`，`n_gpu_layers: 0 / 2` —— **9B 的 33 层只有 2 层在显卡上**。

实测 8G 卡（RTX 5050 Laptop，7070 MiB 可用）：

```
n_ctx=16384  层 33/33 全上卡
   权重 4861M + KV 512M + 计算 588M + 其它 50M ≈ 6011M  → 剩约 1G 余量 ✓

n_ctx=32768  层 33/33 全上卡
   4861 + KV 1024 + 计算 1132 + 50 ≈ 7067M           → 一滴不剩 ✗
```

**改成 `n_ctx: 16384` + `n_gpu_layers: -1`**（两套本地配置都改了）。

收益：

```
窗口   4096 → 转录本预算   2145   允许的提示词   2827 token
窗口   8192 → 转录本预算   4753   允许的提示词   5653 token
窗口  16384 → 转录本预算  10405   允许的提示词  11305 token   ← 现在
```

备份：`酒馆数据/接口配置.json.备份20260919-160213`

## 七、剩余工作（晚上）

> ⚠ **这一节是白天收尾时列的清单，保留原样当历史。** 晚上这几条**一条都没做** ——
> 晚上做的是九到十七节那些事。这一节里唯一被"顺手解决"的是别的方向的问题：
> **本地模型根本没上显卡**（第十四节）。

### 1. 提示词在劝阻 `write_file`
系统提示第 6 条 + `write_file` 的 schema 说明都写着"别用 write_file"。
**新建**文件时这两句是绊脚的（它会先试 `edit_file`，拿到"文件不存在"再绕回来）。
应该改成"**新建**用 write_file；改已有文件的一小段才用 edit_file"。

### 2. 没有"往文件里追加"这个动作
写只有两种：`write_file` 整覆盖、`edit_file` 要求文件已存在。
所以长文件（一个网页）要么一次吐完，要么"先写骨架再一块块补" ——
**而没有任何东西提示模型这么做**。用户那套"分片写 txt 再拼"的绕法就是这么被逼出来的。

### 3. 其他
- **KV cache 量化**没暴露（Q8/Q4 能把 KV 占用砍一半 → 32768 就稳了）
- **「工具协议」开关**（自动 / 原生 / 文本）没上 UI，目前只能改代码
- **云端的窗口读不到**，聊天链路对云端只能按字数控（故意的，见 `本机窗口`）
- **Qt 那一层没测过**（设置框的联动、上下文页的提示行），只做了代码审查

## 九、聊天页的接口自由切换

### 病根

会话建出来的时候只落在"默认那套"（`接口编号 = 0` → 接口配置里最早建的那套），
而**之后没有任何地方能改**。想给某一段对话换个模型，只能改接口配置本身 ——
那就把别的对话一起改了。

### 做法

输入区那条按钮行最左边加一格 `接口 [下拉]`：

- 列**全部**几套配置，**没有"默认"这一项**（用户明确要的：自由切换，别搞"固定/默认"）
- 点了就写进**这一段会话**的 `接口编号`，别的会话不动，新开的对话仍然是"没指定"
- **`编号 = 0`（没指定过）或者指向一套已经删掉的配置时，下拉拨到"实际生效的那套"，
  但绝不回写库** —— `0` 和"指定成第一套"在盘上是两回事，顺手改掉就再也分不出来了

### 坑

1. **下拉是异步填的，而它要跟着会话走。** `刷新` 的工人活原来只读消息，
   于是下拉不知道该拨到哪套。改成**会话行和消息在同一件活里读** ——
   分两次投的话，中间用户切了会话，下拉会拨到别的段上。
2. **下拉宽度得自己用字体量，还得单独设弹出列表的宽度。**
   模型文件名很长（`qwen2.5-3b-instruct-q4_k_m.gguf`），窄了就是省略号，
   用户分不清哪套是哪套。光设下拉自己的宽度不够 —— **弹出那张列表是另一个控件**，
   要 `view().setMinimumWidth(...)` 一起设。
3. **用户报"没有下拉窗"，其实是两回事叠在一起**：他看的是改代码之前开的那个窗口
   （Python 不热更新）；而**刚开软件还没点角色时下拉是灰的、也不说为什么** ——
   点不动、没反应，跟"这功能没做"分不出来。
   加了一格紧跟下拉的小灰字专门说理由（`（先点个角色、挑一段对话，就能换这一段用哪套）`
   / `（一套接口都没配…）` / `（这条说完才能换）`），判据跟 `setEnabled` 同一处算。

## 十、编程助手：转录本落盘 + 「助手上下文页」

### 成果

每跑完一次任务，把「任务原文 + 每一步 + 最后一次真发出去的提示词 + 结局」存盘：

    助手任务.json           {"<编号>": {任务 / 工作目录 / 步数 / 结局 / 时间}}   ← 索引
    助手转录/<编号>.json     {步们 / 存根 / 最后发出去的那一份 / …}            ← 大件

**先写大件、后写索引**（反了就留下"列表里有、点开是空的"）；删则反过来。
查看走新的「助手上下文页」：左列每一步标 `[折]/[发]/[未]`，右列两张页 ——
「发出去的样子」（最后一次的 system + 消息数组）和「这一步的原文」（点某一步切过去，
含 `<tool_call>` 的原文 + 工具参数/结果全文，**一个字不截**）。

**agent 的行为一个字没改**：仍是"一次一个任务"，不跨任务续上下文。

### 关键设计：`交出` 钩子怎么挂

`跑()` 有**十几个出口**（正常答复 / 解析失败 / 空回复 / 没有进展 / 上下文满 /
步数上限 / 用户停了 / 模型报错）。逐个挂钩子必漏，而且将来新增出口就漏一处。

改成：**抄本一建好就交给外面**，跑完（正常返回、`raise`、将来任何新出口）再读它。
一处都不用挂。

### 坑

1. **`折到` 会撒谎。** 撞上硬上限那条路会调 `消息(保留=0)` 把 `self.折到` 推高，
   可它**根本没调模型**。所以界面上标 `[折]/[发]/[未]` 一律用**调模型前冻的那份快照**
   （`{系统, 消息, 小号, 第, 共步, 折到, 原生, 工具名们}`），不用转录本末尾那个 `折到`。
2. **快照必须放在 `调模型` 前面、`try` 外面。** 放 `try` 里面 → 模型抛异常那条路
   没冻上（而那次请求是真的发出去了）；事后重调 `消息()` 复原更糟 ——
   那会二次折叠，而且拿到的可能是"没发出去的那一份"。
3. **左栏一开始是死的。** 第一版只把步骤列出来，点了一点反应都没有，某一步的原文
   根本没地方看。补了点击 → 切到「这一步的原文」。
4. **「刚跑完就关窗」有毫秒级的窗口会丢这次转录**（`_拆面板` 是先 `工位.停()`、
   后 `助手页.关掉()`）。后果只是少一条刚看过的记录，**不值得为它加同步等待**
   （那会让关窗卡住）。写在注释里了。

## 十一、两个「上下文」窗口合成一个

原来聊天一个窗口、编程助手一个窗口，各有一个「关闭」、各有一个入口。

### 做法

`上下文框(QDialog)` = 一个 `QTabWidget` + 两个页：

| | |
|---|---|
| 页 0「聊天会话」 | `上下文页`（改前是 `QDialog`，现在是 `QWidget`） |
| 页 1「编程助手」 | `助手上下文页`（同上） |

- **入口只留主窗一个**（工具条 / 『会话 → 上下文…』/ `Ctrl+K`），助手页顶栏那个按钮摘了
- **默认落在哪一页跟着你正在看的那一页走**：在编程助手页按 `Ctrl+K` 就直接是助手那页
- **"聊天在忙就不给开"这条规矩换掉了**：改成把 `对话页.在忙` 传进去，
  「聊天会话」那页**自己只读**（保存/条数/字数/提示框/**左栏列表**全灰 + 写明原因）。
  理由：合并之后那条规矩会把「编程助手」那页一起挡在外面，而那页跟聊天无关。

### 坑

1. **`_可改` 必须放 `_画` 的最后一行。** `_画预览` 结尾会把 `报错` 那格清空（它在清上次的错），
   而只读说明也写在同一格 —— 放前面会被它抹掉。
2. **`改过了` 必须用属性透传**（壳 → 会话页），不能在壳里复制一份：复制的话
   会话页内部置了 `True`、壳上还是 `False`，表现就是"在框里删了消息，回来那条还画着"。
3. **一个窗口里不能有两个「关闭」** —— 用户不知道该按哪个，而且 `reject()` 打在
   不是对话框的控件上没有意义。两个页类都降成 `QWidget`，"关窗"归壳统一管。

## 十二、上下文记忆

### 是什么

**一串条目（每条可启用/停用），启用的拼进提示词。** 两条来源：

- **手写**：在「上下文」里点「新增一条」
- **自动回收**：聊天时被挤出窗口的旧消息、助手任务里被折叠掉的步骤，
  自动收成**停用的候选**（标 `[自动]`），等用户过目。**默认停用 —— 这就是
  它不会污染提示词的原因。**

挂载点：聊天挂**角色**（跨该角色所有对话共享），agent 挂**工作目录**。
落地是"索引小表 `记忆` + 大件 `记忆/<编号>.json`"（跟 `助手任务`+`助手转录` 同构）。

### 坑（这一节最多）

1. **真正发出去的系统提示不在 `酒馆对话页._拼` 里拼，而在 `_摆气泡` 又拼了一次。**
   `_拼` 调 `窗口内` 只为了拿裁完的 `消息们`，`系统` 被丢掉。所以：
   - 只在 `_拼` 注入 → **功能静默不生效**
   - 只在 `_摆气泡` 注入 → `窗口内` 裁 token 时**不知道记忆占了多少** →
     提示词越过 `n_ctx` → llama.cpp **从最前面截断、先丢系统提示**，界面上毫无症状

   **修法：走 `设定` 的保留键 `设定['__记忆__']`。** `拼提示` 有三个调用点
   （`窗口内` 内部、`_摆气泡`、上下文页的预览），而 `设定` **是唯一能同时到达
   这三处的同一个对象**。参数化的话漏掉任意一处都是上面那两种坏法之一。
   ⚠ 这条键**绝不能落盘**（它是那一轮的临时数据），`上下文页._保存` 是"当场重读
   `段.设定()` 再改三个键"，两边都写了注释点名。

2. **位置定死：插在 ⑤（用户自己写的会话系统提示）之后、⑥ 之前。**
   挪到最末尾会把 ⑦`本地规矩` 挤走 —— 那条是靠"离生成最近"起作用的，挤走它
   模型会不听扮演规矩。

3. **自动回收没有水位 = 用户删掉的候选每轮复活。** 回收是"从消息流里现算"的，
   一条老消息只要还老在边界外面，每轮都会被算成待收 —— 用户嫌烦删掉，下一轮它照样回来，
   **永远删不掉**。
   修法：`记忆` 索引行里加一列 `回收水位 = {会话编号: 已处理到的最大序号}`，
   只收水位之外的；收完**在同一次 `独占` 里推水位**（分两次的话中间死掉就是
   "条目收了、水位没动"）。
   代价（说清楚）：**重说/编辑一条已经被收过的老消息，记忆里那份不会更新**
   （序号低于水位，不再被看第二眼）。宁可漏一次更新，也不要每轮把用户删过的东西塞回来。

4. **去重键必须带内容指纹。** 消息序号**会被复用**（`下个序号` = 当前最大 + 1，
   删掉末尾那条之后新消息拿同一个号），而 `覆盖消息` 又保留原来的 `创建于`。
   只按 `(会话, 序号)` 去重会"漏收 + 串内容"。
   规则：同 `(会话,序号,指纹)` 跳过；同 `(会话,序号)` 但指纹不同时，
   **只有那条还是「自动 + 停用」（用户从没碰过）才替换**；用户启用过/手改过的永不覆盖。

5. **边界取"幸存者里最小的序号"，不是"候选里被丢掉的"。**
   比「条数」更老的消息根本没进候选，按候选算的话**它们永远收不到** ——
   而那些恰恰是最该被记住的。`留下` 为空时一条都不收（否则边界当 +∞，会把整段历史一次收光）。

6. **渲染必须确定性**（不带时间戳、顺序稳定）：记忆在系统提示里，而 llama.cpp
   只复用"和上次完全一样的前缀"的 KV。渲染每轮抖一下就等于每轮从 System 那段起全部重算。
   上限也要跟 `n_ctx` 挂钩（`窗口//8`），界面上的"带了 N 条 / 没带 M 条"
   **取 `渲染` 的返回值**，不另数一遍。

7. **改记忆要提示"下一轮会慢"**：插入点之后整段 KV 作废。

8. **助手页 `_开工` 改成两段式**（它主线程、没有 `库`，而 `助手线` 不许碰存储）：
   投活读项目记忆 → 回调里再排活。三个闸：**投活前先锁界面**（防重入）、
   回调判 `_关过`/`_跑中`/`在跑`、**目录捕获成局部变量**（不然回话期间换了目录，
   会拿旧目录的记忆去跑新目录的任务）。

9. **助手收折叠存根进项目记忆时，不能用 `(会话,序号)` 去重** —— 助手没有那两样，
   `(0,0)` 会让所有候选互相顶掉、只剩最后一条。加了 `按序号去重=False` 那条路。
   （第一版就是这么错的，靠一条断言抓出来的。）

## 十三、接口配置分两条路线

### 要什么

给 agent 调 0.2 的温度（别绕路）**不该把聊天也带走**。聊天要 0.8（说话有味道）。

### 做法

`接口配置` 加一列 `用途`（`对话` / `agent` / `''`）：

- 聊天那条链只认「对话」的，编程助手只认「agent」的
- 接口配置页左上多一档「看哪一组」，列表只显示那一组
- **`''` 是"老数据"**（这一列是后加的）：语义是**两边都能用、两边都看得见**，
  列表里标「← 旧配置：两边都能用」。
  ⚠ **不自动给老数据打标签** —— 那是替用户改数据，改错了还找不到原因。

### 坑

1. **`默认()` 不筛用途 = 聊天静默用上 agent 那套。** `接口编号 = 0` 的会话会落到
   `默认()` 上，而它原来是"整张表里最早建的那套" —— 没筛的话可能挑到给 agent 配的
   （温度 0.2、可能还带别的设置）。表现是"聊天莫名其妙变了个人"，而两边都看不出为什么。
   **验证时专门造了一条编号更小的 agent 配置来卡这条。**
2. **"编号对得上但用途不对"也要兜。** 用户把 agent 那套改成「对话」之后，
   原来指着它的会话不该拿到 agent 配置 —— 跟"那套配置被删了"是同一种情形，
   兜到这一组的默认上。
3. **`清单列` 漏加 `用途`** → 列表行读不到这一列、`从行` 给默认值 `''`，
   于是**所有配置在界面上都显示成"旧配置"**。不报错、只是不对，跟 `主键列` 那类漏加同一种坏法。
4. **助手那条路要多拦一道。** `助手设置` 里记的编号可能指着一套已经被改成「对话」的配置，
   `取或默认(n, 'agent')` 会兜到别的 agent 配置上。所以 `酒馆助手线._干` 里加了一条
   明确报错：**"这套的「给谁用」填的是对话，所以编程助手用不了它"** ——
   不说清是"配错组了"，用户会对着一个明明能用的本地配置猜半天。

### agent 专用预设参数（同一轮里加的）

用户问"怎么只有角色扮演的预设按钮"。补了「agent 推荐」：

| | 角色扮演推荐 | agent 推荐 |
|---|---|---|
| temperature | 0.8 | **0.2** |
| top_k | 40 | 20 |
| repeat_penalty | 1.10 | **1.05** |
| max_tokens | 1024 | **不动** |
| GPU 层数 | 不动 | **-1** |

- **温度 0.2 是这条最要紧的**：角色扮演要它"有味道"，agent 要它"照做" ——
  温度高了它会反复解释打算干什么、换个说法重来、自己发挥，全是白等的秒数
- **复读罚不能照搬 1.10**：罚狠了模型会为了躲开重复词而绕路，反而更慢
- **不动 `max_tokens`**：编程助手那一步的输出上限由「设置…」里的「单步输出」说了算
  （`跑一轮` 显式盖掉），**这一格 agent 根本不看** —— 填了只会让人以为它有用
- **`n_ctx` 仍然不动**（那是"留多长历史"的取舍），但 `GPU 层数` 现在顺手拉 -1
  （理由见下一节）

## 十四、性能这一场：从"模型太慢"到"层根本没上卡"

用户先后报了三次"慢"，每次的说法都不一样，最后自己一句话点到根上：
**"慢在模型没有完全在 GPU 上"** —— 他是对的。

### 14.1 先排掉三个嫌疑（都没有实测支持）

| 嫌疑 | 实测 | 结论 |
|---|---|---|
| Qwen3 的思考模式开着 | 模板里确实有 `enable_thinking`，但**不传就是走 else 分支**（塞一个空 `<think></think>`）；转录里也没有任何思维链痕迹 | **不是它** |
| `n_batch` 太小拖慢 prefill | 512 与 2048 逐秒相同（3.28 / 3.28 秒） | **不是它** |
| 提示词太长 | prefill 有 1500 token/秒，几千 token 只要一两秒 | 不是主因 |

### 14.2 一个查实的结构性问题：前缀缓存全废

llama.cpp 自己打的日志：

    Llama.generate: 3920 prefix-match found but partial kv removal not supported,
                    re-evaluating full prompt

**根因是模型的架构**：`Qwen3.5-9B` 是**混合架构**（元数据里有 `qwen35.ssm.*`，
还有 `full_attention_interval = 4` —— SSM 层 + 每 4 层插一个全注意力）。
**SSM 的循环状态没法从中间截断**，所以"把 KV 砍回公共前缀"这个操作对它不成立，
llama.cpp 只能退回全量重算。实测：第二轮只多 200 token，照样要 3.46 秒。

**试过绕过去，失败了，已整段撤回**：纯追加的对话根本不需要"截断"，
所以我在 `generate` 上补了一条快路（旧 token 全是新提示词前缀时 `reset=False`、只喂增量）。
结果**一次都没走上**。抓分岔点抓到真因：

    旧: ...<|im_start|>assistant\n <think>\n\n</think>\n\n 没问题，我已经准备好…
    新: ...<|im_start|>assistant\n 没问题，我已经准备好…
                                  ↑ 第 824 个 token 就在这里岔开

模板只在**生成那一刻**往 assistant 标记后面塞那段空思考块，
**重新渲染历史时不塞**。想把它补回 `content` 里也没用 ——
模板有一句 `{%- if '</think>' in content %}`，会把它**拆出来吃掉**。
这条路在这个模板上走不通，**代码已恢复原样**。

> **顺带得到一个反直觉的结论**：既然前缀复用本来就不生效，
> **折叠（改写历史中段）就没有缓存代价了** ——
> 所以"上下文调小 / 更早折叠"现在是**纯赚**。
> 这跟原来的设计假设（"折一次要重付一次 prefill"）正好相反。

### 14.3 量出来的基线（9B Q4_K_M / n_ctx=16384，全上卡）

    单次调用的固定开销   63 token 的提示 → 0.06 秒（几乎为零）
    prefill             823 token → 0.51 秒；4023 → 2.64 秒；16023 → 12.30 秒
                        ≈ 1500 token/秒（越长略降，16023 时 1184）
    decode              ≈ 25–35 token/秒

**算一笔账**：写一个四则运算器脚本（1485 字 ≈ 900 token）**光生成就要 30 秒**；
一个 40 秒的任务里 35 秒以上是"一个字一个字往外写"。**decode 才是大头。**

### 14.4 真正的根因：模型是纯 CPU 在跑

查盘上的配置：

    千问-9B（agent）  采样参数 = {"n_ctx": 4096, "n_gpu_layers": 0, ...}
                                          ↑↑↑ 0 = 一层都没上显卡

`n_gpu_layers = 0` 就是**纯 CPU**。而它怎么变成 0 的：

- 接口配置页**空白表单**那两格的默认值就是 `n_ctx = 4096` / `GPU 层数 = 0（纯 CPU）`
- 而两个"推荐"按钮当时**故意不动这两格**（理由写的是"那是显存的事，跟风格无关"）
- 于是**任何新建的本地配置，生下来就是纯 CPU 的**，而且**没人会想到去动那一格**

这个理由站不住：**对本地模型来说，"上不上显卡"比采样参数要紧得多**，
而它恰恰是唯一没人会去碰的那一格。

### 14.5 修复

1. **空白表单默认值**：`GPU 层数` 0 → **-1（全上 GPU）**；`n_ctx` 4096 → **8192**
   （`_填表单` 的兜底值同改；但**配过 0 的照样回填 0** —— `is not None` 那一步不能省，
   不然"我故意用 CPU 跑"会被界面悄悄改掉）
2. **两个推荐按钮顺手把 `GPU 层数` 拉成 -1**（提示文字里也明说）
3. **数据修复**：把那两套的 `n_gpu_layers` 改回 -1、`n_ctx` 恢复到 16384

### 14.6 实测验证

    加载前  nvidia-smi:  550 MiB,   3 %
    加载后  nvidia-smi: 6641 MiB,  34 %     ← +6.1G，权重全进去了
    生成中  nvidia-smi: 6805 MiB, 100 %     ← GPU 吃满
    prefill: 5221 token / 3.45 秒 = 1514 token/秒

**判"有没有上卡"最快的一眼**：加载前后 `nvidia-smi` 的显存差。
全上卡 +6.1G；纯 CPU 只跳几百兆。而 prefill 上千 token/秒 = 在卡上，只有几十 = 还在 CPU。

### 14.7 我自己在这一节踩的坑（值得单记）

第一遍改数据的时候，我图省事用了 `酒馆接口.列()` 拿配置行 ——
而**列表行故意不含 `采样参数`**（`清单列` 里没有它）。于是 `套.参数()` 读出来是空字典，
写回去就把用户设的温度 / top_k / repeat_penalty / max_tokens **全清了**，
而且**一点报错都没有**。

靠动手前留的备份捞了回来，第二遍改用 `取()`（整条）才做对。
`酒馆接口页` 的注释里本来就写着这条规矩，我还是踩了 —— 结论是：
**动用户数据之前先备份，改完立刻读回来对一遍。**

## 十五、这一轮踩的坑（汇总）

| # | 症状 | 真因 | 修法 |
|---|---|---|---|
| 1 | 功能静默不生效（记忆没发出去） | 真正发出去的 system 是 `_摆气泡` 拼的，不是 `_拼` | 走 `设定['__记忆__']` 这个三处都能到达的对象 |

| 4 | 漏收 + 串内容 | 消息**序号会被复用**，只按 `(会话,序号)` 去重不够 | 去重键带**内容指纹**，用户碰过的永不覆盖 |

| 6 | 助手回收的候选互相顶掉、只剩一条 | 助手没有"会话/序号"，`(0,0)` 让它们同名 | `收待定(..., 按序号去重=False)` |
| 7 | 聊天静默用上 agent 那套配置 | `默认()` 没按用途筛 | `列/默认/取或默认` 都加 `用途` 参数 |
| 8 | 所有配置都显示成"旧配置"、改不动 | `清单列` 漏加 `用途`，缺列填默认值 `''` | 加进 `清单列` |
| 9 | **本地模型每秒三五个字** | **新建配置的空白默认值是 `n_gpu_layers = 0`（纯 CPU）** | 默认改 `-1`；预设按钮顺手拉满；数据修复 |
| 10 | 采样参数被清空（我自己造成的） | 用 `列()` 拿列表行去改，而它不含 `采样参数` | 改用 `取()` 整条；动数据前备份 |

## 十六、验证方式与边界（晚上这一轮）

**跑出来才算数的：**

- 全项目 `py_compile`（每一轮改动之后都跑）
- **离屏 Qt**：两个上下文框的页签与只读行为、记忆板的增删改与忙时行为、
