● 好问题，这正是那个脚本故意不做清单的原因。核心是一句话：

  │ PyInstaller 不是读清单，是"跟着 import 走"。

  它怎么知道该打什么

  打包第一步叫「分析」（Analysis）：从入口脚本开始，读它的字节码，把里面每一条 import X / from X import y 当成一条边，然后 BFS 下去 —— 酒馆.py → 酒馆窗口 → 
  酒馆助手页 → 酒馆助手 → 本地agent协议 → …

  该打什么，是算出来的，不是声明出来的。

  ⚠ 有个常见误解值得先掐掉："写在函数里的 import 会不会看不见？" 不会。它扫的是字节码，不是文件头那几行 —— 一个模块里所有代码对象（含函数、类、里面套的）的
  IMPORT_NAME opcode 都会被收到。酒馆本地.py:576 那句 import 本地agent协议 在函数外，但就算挪进函数也一样找得到。

  而且它是过近似：if False: 里的、从来没被调用的函数里的，照样收。方向是安全的。

  所以清单为什么"不需要列"

  因为清单会烂，推导不会：

  ┌────────────────────┬──────────────────────────────────────────────────────────────────────────────────┬──────────────────────┐
  │                    │                                     手写清单                                     │    跟着 import 走    │
  ├────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────┤
  │ 加一个模块忘了登记 │ 不报错，就是没打进去 —— 等到运行时那一步才炸，或者更糟：冻结里静默退化成别的样子 │ 不可能发生           │
  ├────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────┤
  │ 改个名字           │ 清单里留着旧名，报一条 warning 就过去了                                          │ 自动跟着变           │
  ├────────────────────┼──────────────────────────────────────────────────────────────────────────────────┼──────────────────────┤
  │ 谁负责维护         │ 人                                                                               │ 没人，它在构建时重算 │
  └────────────────────┴──────────────────────────────────────────────────────────────────────────────────┴──────────────────────┘

  这个项目在别处早就栽过同一类跟头（tool_call vs tools、各种手写表），所以这条不是洁癖，是同一套判据：凡是能推导的，就不该手写第二份。

  那 --hidden-import 是干嘛的

  它是"补贴静态分析的盲区"，不是"清单"。 补的是"分析看不见"的那几类，判据是能不能从源码里看见那个名字：

  看得见  →  import 本地agent协议        （字面量）
  看不见  →  importlib.import_module(名)   （名字是运行时才知道的字符串）
             __import__(名)
             exec("import ...")
             字符串拼出来的模块名 / 插件目录扫出来才发现的模块

  我核过这个项目：业务代码里一个动态 import 都没有 —— importlib / __import__ / spec_from_file 在 打包.py 以外零命中（grep 出来的 exec( 全是 
  QDialog.exec()）。

  所以 打包.py:824 那圈 --hidden-import=自家 是双保险，不是让它 work 的那一环。它存在的意义是：万一以后有人写了动态 import，或者 PyInstaller
  某天漏扫了某个模块，这一圈能兜住。--hidden-import 补多了不报错（已经在图里的再补一遍是幂等的），所以这个保险是白拿的。

  ⚠ 但"能补"不等于"随便补"

  --hidden-import 的语义是无条件把整个模块子树拉进 exe，连带它的依赖。所以：

  - 我们自己写的、只用标准库的业务模块 → 可以无脑补（就是那 24 个）
  - 第三方包 → 一个都不能补 —— 那些正是要 --exclude-module 排出去、留在 依赖库/ 里的。补进去等于把 exe/依赖库 的切分搞破

  扫标准库需求（打包.py:524）那段注释把这条写死了：

  │ 第三方模块一概不要 —— 那些正是要留在 依赖库/ 里的东西，补进 exe 就白拆了。

  而且那一整段函数存在的理由，就是"推导的盲区"的另一个实例，只是这个盲区是我们自己拆出来的：--exclude-module 把依赖的代码排掉了 → PyInstaller 的静态图走不进
   urllib3 的代码 → 就看不见里面那句 from http.client import IncompleteRead → exe 起来了、PySide6 也起来了，然后死在 ModuleNotFoundError: No module named 
  'http'（注释里写着这是实打实踩到的第一版死法）。

  拆包拆出来的盲区，得自己扫回来补上 —— 这是 --hidden-import 的第二种用法，也是这个脚本里唯一一处"必须自己列"的地方（列的是标准库，不是模块清单）。

  最后一层：hidden-import 解决不了的那一半

  它只管模块。"按路径找同级文件"的东西它一概看不见 —— llama_cpp 是 __file__ 找同级 lib/llama.dll，PySide6 是 os.add_dll_directory。这些没有 import 可跟。

  所以那部分必须手写检查，而且都在出口校验里摆着（打包.py:1050-1061）：llama_cpp/lib/llama.dll、PySide6/plugins/platforms、python3.dll。

  一句话收尾：能推导的推导，推导看不见的（动态 import / 被自己排掉的代码 / 按路径找的文件）才手写补，而且补的范围要尽量窄。 
  手写清单的问题从来不是"写得不对"，是"它不会自己发现你忘了写"。
